# Part VIII · Architecture — revision sheet
*Chapters [23 · Distributed Systems & Microservices](23-distributed-systems-microservices.md) · [24 · System Design for Java Architects](24-system-design-for-java-architects.md) · [25 · Security for Java Engineers](25-security-for-java-engineers.md)*

## Distributed systems
- **A network call can fail, time out, or succeed while you think it failed.** Know the eight fallacies (the network is reliable, latency is zero, …).
- **Default to a modular monolith** with enforced module boundaries; extract a service for independent scaling, independent deployment, different reliability or security requirements, or a different technology. Otherwise you build a **distributed monolith** (lockstep deploys, shared databases, synchronous call chains). Conway's law: design team and service boundaries together.
- **CAP:** during a partition, choose consistency or availability. **PACELC:** *else* choose latency or consistency. Spectrum: linearizable → sequential → causal → read-your-writes → monotonic reads → eventual. Name the guarantee **per operation**.
- **Quorums:** **R + W > N** makes read and write sets overlap (N = 3, W = 2, R = 2 tolerates one failed replica). Sloppy quorums and hinted handoff weaken this.
- **Dual writes** (database save + `kafka.send` in one method) lose or invent events → **transactional outbox** in the same transaction, relayed by polling (`FOR UPDATE SKIP LOCKED`) or CDC (Debezium). The guarantee is **at-least-once**, so consumers deduplicate (an **inbox** table).
- **Idempotency keys:** generated by the client once per logical operation; a unique constraint on the key; store and replay the **response**; the same key with a different payload → 422; a TTL; an "in progress" state.
- **Sagas instead of 2PC:** local transactions plus **semantic compensations** (refund, not rollback). Put hard-to-compensate steps after the **pivot**. Sagas lack isolation, so use semantic locks (`PENDING_STOCK`). Every step is idempotent; persist saga state (Temporal, Camunda).
- **Event sourcing** where the history *is* the business (ledgers, trading); otherwise state storage plus an outbox. **CQRS** can be as light as SQL projections in the same database.
- **Kafka:** ordering only **within a partition** (key = aggregate ID); consumer-group parallelism ≤ partitions; at-least-once = process, *then* commit; exactly-once covers effects **inside Kafka** only. Producer: `acks=all`, idempotence (default since 3.0). Pitfalls: processing longer than `max.poll.interval.ms` → rebalance storms; poison pills → bounded retries then a dead-letter topic; partition count is hard to change for keyed topics; alert on **consumer lag**. Kafka 4.0 removed ZooKeeper (KRaft).
- **Caching:** cache-aside with delete-on-write and **TTLs on everything** (the cache-aside race can leave stale data forever). Stampede → single-flight loading (Caffeine `get(key, loader)`); avalanche → jittered TTLs; penetration → negative caching or a Bloom filter; hot keys → a near-cache.
- **Coordination:** don't implement consensus (Raft: majority commit; 2f + 1 nodes tolerate f failures). **A lock holder can't know it still holds the lock** (GC pauses outlive leases) → **fencing tokens** checked by the storage, or a single writer per key.
- **Time:** never order events across machines by wall clock. `nanoTime` measures durations within one JVM; Lamport and vector clocks; in practice, a single sequencer per key.
- **Mesh retries plus application retries multiply** (3 × 3 = 9×): one layer owns retries and timeouts.
- **API evolution:** additive changes only; tolerant readers; version when you must break; events are APIs with longer lifetimes (schema registry, contract tests).

## System design
**The interview loop (45–60 min):** clarify (5) → estimate (3–5) → API and data model (5–10) → high-level design (10) → deep dives you choose (15–20) → trade-offs and evolution (5). Always ask about scale, p99 targets, availability, per-operation consistency, durability, geography, compliance and cost.

| Number | Value |
|---|---|
| Seconds per day | 86,400 ≈ 10⁵ |
| 1 M requests/day | ≈ 12 QPS average (1 B/day ≈ 12K QPS) |
| Peak ÷ average | 2–5× |
| Redis, one shard | ~100K+ simple ops/s |
| Single PostgreSQL primary | thousands to tens of thousands of simple writes/s |
| Base62, 7 characters | 62⁷ ≈ 3.5 × 10¹² codes |
| Snowflake ID | 41-bit ms timestamp · 10-bit worker · 12-bit sequence ≈ 4K IDs/ms per worker |

- **Consistent hashing (measured, 100K keys, 3 → 4 nodes):** `hash % N` moved **75%** of keys; the ring moved **~26%** (ideal 25%); without virtual nodes one node got 12.6% of keys and another 47.4%. In production, pre-split into many more partitions than nodes.
- **IDs:** UUIDv4 fragments B-tree indexes; **UUIDv7** is a good default; opaque public IDs prevent enumeration (but they're not authorization).
- **Rate limiting:** a token bucket allows bursts up to *b*, then sustains *r*; fixed windows allow 2× bursts at edges. Distributed: a Redis Lua script, local limits, or hybrid; decide fail-open vs fail-closed per use case; respond `429` with `Retry-After`.
- **B-tree vs LSM:** read-heavy and transactional vs write-heavy with compaction.
- **Payments:** idempotency everywhere; a persisted state machine with guarded transitions; an immutable double-entry ledger; `long` minor units or scaled `BigDecimal`; **a timed-out PSP call is unknown, not failed** (query by idempotency key); daily **reconciliation**; tokenise cards to shrink PCI scope.
- **Job scheduler:** `SKIP LOCKED` claiming, leases plus heartbeats, a reaper for expired leases, DST-aware cron in the job's time zone, misfire policy, lag as *the* SLI.
- **Chat:** WebSocket gateways plus a connection registry; persist first, then a per-conversation sequence, then fan out; pull for huge groups; dedup by message ID.
- **Migrations:** strangler fig; CDC over dual writes; backfill; shadow reads; cut over reads, then writes; every step reversible.
- **Multi-region:** RPO (data you can lose) vs RTO (time you can be down); active–active needs conflict handling or a home region per user; **cells** limit the blast radius.
- **Communicate:** C4 levels 1–2, a design doc (context, goals/non-goals, proposal, two or more alternatives, risks, rollout and rollback, SLOs), ADRs for individual decisions.

## Security
- **Mindset:** trust boundaries, STRIDE per component, defence in depth, least privilege, secure by default. Broken access control is the #1 OWASP risk.
- **Injection:** bind parameters (JPQL concatenation is still injection); **identifiers can't be bound**, so allow-list them; `ProcessBuilder` with an argument array; never evaluate user input as SpEL/OGNL; path traversal and Zip Slip (normalise, then `startsWith(base)`).
- **XXE:** harden every XML parser factory. **Deserialisation:** no Java serialisation across trust boundaries. **SSRF:** allow-list hosts; resolve once, validate the IP, connect to that IP; re-validate redirects; egress controls.
- **Passwords:** Argon2id, bcrypt, scrypt or PBKDF2, never fast hashes. `DelegatingPasswordEncoder` stores the algorithm ID so you can migrate at login. Rotate the session ID at login; `HttpOnly`, `Secure`, `SameSite` cookies; CSRF protection for cookie-authenticated apps; generic login errors.
- **OAuth/OIDC:** Authorization Code + PKCE for anything with a user; Client Credentials for service to service; implicit and password grants are gone in OAuth 2.1. **Never send an ID token to an API.**
- **JWT:** reject `alg: none`; pin the algorithm per key (RS256 → HS256 confusion); validate `iss`, `aud`, `exp`, `nbf`; 5–15 minute access tokens; no tokens in `localStorage`; JWKS with `kid` for rotation.
- **Authorization:** deny by default, enforce in the service layer, check ownership in queries (IDOR), tenant scoping plus row-level security.
- **Crypto:** `SecureRandom`; HMAC compared with `MessageDigest.isEqual`; **AES-GCM with a fresh 96-bit IV** (never ECB, never reuse an IV); Ed25519; HKDF (JDK 25); ML-KEM and ML-DSA (JDK 24). Keys in a KMS; envelope encryption; crypto-shredding.
- **TLS:** keystore = your identity, truststore = whom you trust; never a trust-all `TrustManager`; monitor certificate expiry.
- **Secrets:** a vault, mounted as files (`configtree:`), short-lived identity-based credentials; heap dumps and JFR files can contain secrets.
- **Supply chain:** Log4Shell's lessons are SBOMs, patch velocity, egress restrictions, and never interpreting data as code. The Security Manager is permanently disabled in JDK 24 (JEP 486), so isolate at the process or container level.

## Say it in one breath
- "Distribution is a cost we pay for organisational or scaling benefits; I'd start with a modular monolith."
- "The outbox turns a dual write into one local transaction plus at-least-once delivery, so consumers must be idempotent."
- "Lease-based locks without fencing aren't safe for correctness."
- "A timeout is an unknown outcome, not a failure."
- "Authentication says who you are; authorization, checked on every object, says what you may touch."
